# 버추얼 트라이온 키오스크 SaaS — 전체 설계 문서

> 이 문서는 프로젝트의 단일 진실 출처(single source of truth)다.
> 비즈니스 모델 · 제품/UX 비전 · 기술 지형 · 하드웨어 · 설계 원칙 · 단계별 계획을 모두 담는다.
> 기간은 정하지 않음. 시간 날 때마다 작업, Phase 단위로 진행. 플랜은 유동적으로 가져간다.

---

## 0. 한 줄 요약

매장과 계약하는 **B2B SaaS**. 점주가 옷을 등록하면, 매장 키오스크에서 손님이 그 옷을
(기본 마네킹 또는 본인 사진으로) 입은 모습을 보고, 좌우로 돌려가며 다면을 확인한다.
최종 지향점은 자연스러운 자유 회전과 옷 나풀거림이지만, 단계적으로 오른다.

---

## 1. 비즈니스 모델

- **고객:** 매장(B2B). 매장과 계약해 키오스크/서비스 제공.
- **콘텐츠 공급:** 점주가 직접 옷을 등록(셀프 온보딩). → "옷 등록 파이프라인"이 숨은 핵심 제품.
- **입력 제약(설계를 못 박는 결정적 사실):** 점주는 **평면 옷 사진**(앞·뒤 정도)만 올린다.
  - ⟹ 옷마다 3D 모델링/리깅하는 방식은 이 사업모델과 **구조적으로 불가**.
  - ⟹ 후보 기술 = 평면 사진 한두 장에서 동작하는 **디퓨전 기반 VTON**으로 한정.
- **과금 설계:** 생성당 비용 구조. "가벼운 이미지 미리보기 → 마음에 들면 무거운 생성 1회"로
  GPU 비용을 단계적으로 통제 (특히 영상은 이미지보다 GPU를 훨씬 많이 먹음).
- **멀티테넌시:** 매장별 카탈로그·계정·과금 분리.

### 해자(moat)는 어디 있나
단순 API 래퍼는 누구나 함 → 해자 없음. 진짜 차별화는:
1. **다면/모션 경험** (정적 한 장이 아니라 회전·움직임) — "와" 포인트.
2. **옷 등록 파이프라인 품질** (막 찍은 사진 → 정제 → 모델 입력) — 운영 노하우, 모방 어려움.
3. **자체 파인튜닝 모델** (입력 형식·미감 특화) — 마진·품질 통제.

## 2. 제품 / UX 비전

키오스크 화면 흐름:
1. 매장 상품들이 나열됨.
2. 상품 선택 → **기본 마네킹/모델**이 그 옷을 입은 모습. (자기 사진 보기 싫은 사람용 기본값)
3. "착용샷 보기" → **정면 전신 사진 1장** 촬영.
4. 그 사진의 사용자가 자연스럽게 합성됨(진짜 사람처럼).
5. 좌우 스크롤 → 몸이 돌아가며 모든 면 확인.
6. (지향) 자연스러운 포즈/움직임, 옷이 나풀거림.

UX 메타포: **동물의 숲의 옷 미리보기**(가운데 서 있다가 좌우로 돌아가는 그 느낌).

### 핵심 통찰
- **마네킹 모드 = 큰 이득.** 스톡 모델은 고정 ⟹ 점주가 옷 등록하는 순간 백그라운드에서
  여러 앵글을 미리 합성·캐싱 ⟹ 키오스크에선 **대기 0초**. 사용자 사진 모드만 실시간 경로.
- **"실시간"의 재정의.** 거울처럼 라이브로 따라 움직이는 건 사실상 불가(연구실 R&D급).
  현실 버전은 "사진 찍고 → 몇 초 뒤 결과"의 **즉석(on-the-spot)** 방식.

## 3. 핵심 기술 현실 / 긴장

> **사진 같은 사실감**과 **자유로운 실시간 회전**이 지금은 서로 잡아당긴다.

- **디퓨전 VTON**: 사실감 좋음. 단, 한 앵글당 한 번 생성(수 초). 슬라이더로 부드럽게 못 돌림.
  ⟹ 현실 버전 = **이산 회전**(정면/좌사선/측면/후면을 미리 렌더해두고 화살표 전환). 동물의 숲의 *툭툭* 도는 느낌.
  ⟹ 부드러운 회전은 영상 VTON으로 "도는 클립"을 미리 렌더해 재생.
- **3D 복원**: 슬라이더 자유 회전 + 천 시뮬레이션 가능. 단, 정면 사진 한 장에서 **뒷모습은 모델이 상상**(under-constrained). 현재 논문 단계.

### 이게 허황된 게 아니라는 증거 (2025–2026 연구)
- **VTON 360**: 2D VTON을 다중 뷰 의류 + SMPL-X 노멀맵으로 확장, 임의 각도 착용 시도.
  (단, 논문 스스로 "전 시점 지원 고해상 3D VTON은 미해결 과제"라 명시.)
- **HumanOrbit**: 단일 이미지 → 비디오 디퓨전으로 연속 회전 생성 → 텍스처 메시 복원.
  (단, 한 장 복원은 자기 가림 때문에 근본적으로 제약 큼.)
- **HumanLift**: 단일 이미지 → 3D 가우시안 스플래팅 사실적 복원 (자유 회전을 가능케 하는 표현).

⟹ 6단계는 "불가능"이 아니라 "2026년 현재 논문이 막 풀고 있는 것". 솔로 제품화는 아직 이름.

## 5. 기술 지형 & 모델 맵

- **이미지 VTON:** CatVTON(가벼움), IDM-VTON(사실감 ↑, 깔끔한 입력+안정 마스킹 필요)
- **멀티뷰 / 360:** VTON360, GaussianVTON
- **영상 VTON:** ViViD, SwiftTry(ViViD 대비 60%+ 빠름), CatV2TON, DPIDM
- **단일 이미지 → 3D/오빗:** HumanOrbit, HumanLift, PSHuman

> 단일 학습 출처: **GitHub `Zheng-Chong/Awesome-Try-On-Models`**
> (이미지/멀티뷰/영상 논문·코드·가중치를 시간순 정리. 1→6단계 로드맵을 그대로 추종 가능.)

### "자체 VTON 기술"의 정의
= 기존 오픈모델을 **호스팅·파인튜닝**하는 것 (혼자 수개월, 가능).
≠ 새 아키텍처 발명 (연구실/박사급). 전자만으로 해자 충분.

### ⚠️ 라이선스 제약 (Phase 0 Step 1에서 확정한 사실)
CatVTON 은 코드·체크포인트·데모 전부 **CC BY-NC-SA 4.0 (비상업)**.
⟹ CatVTON 은 배우고 프로토타입 짜는 도구이지, 그 위에 상용 제품을 올릴 수 없다.
⟹ Phase 3(자체 파인튜닝/모델 소유)가 단순 "해자"가 아니라 사실상 필수인 이유.
상세는 `docs/LICENSES.md`.

## 6. 하드웨어

| 작업 | 어디서 |
|---|---|
| 앱/백엔드/프론트 개발, 전처리 로직, 작은 실험, 오케스트레이션, 모델 호출 클라이언트 | **맥미니 M4** |
| VTON 추론, 파인튜닝, 멀티뷰/영상/3D 생성 | **클라우드 GPU** (RunPod / Vast.ai / Modal / Lambda) |

**M4는 모델 학습·무거운 추론용 GPU로 부적합:**
VTON 모델은 PyTorch+CUDA(NVIDIA) 전제 + VRAM 다소비. 전처리 스택(휴먼 파싱·포즈·마스킹)이
CUDA에 묶여 MPS에서 고통스럽고, 파인튜닝은 M4에서 사실상 불가.
애플 실리콘 추론이 성숙 중이나 원시 연산은 NVIDIA보다 낮고 MPS는 메모리 제약에 걸림.

**단, 이 분담은 임시방편이 아니라 올바른 프로덕션 구조.**
6단계 영상/3D는 어차피 클라우드 GPU 필수 ⟹ 처음부터 "모델 = 원격 워커"면 나중에 안 갈아엎음.

참고: CatVTON 추론 자체는 가볍다 — bf16 에서 1024×768 생성에 약 8GB VRAM. 임대 GPU 부담 작음.

## 7. 변하지 않는 설계 원칙 (6단계를 살려두기 위해 — 모든 Phase 공통)

1. **엔진은 인터페이스 뒤에.** `TryOnEngine` 계약만 고정.
   - 입력: `{ person_image | preset_model_id, garment_assets, options }`
   - 출력: `TryOnResult` (버전 있는 미디어 번들)
   - 뒤 모델은 이미지→멀티뷰→영상→3D로 갈아끼워도 앱은 안 건드림.
   - 코드: `worker/engine/base.py` + `shared/schemas.py`
2. **결과 = 미디어 번들.** 단일 PNG 아님. `views: [{angle, image}], clip?, asset3d?`.
   뷰어는 처음부터 N개 앵글/클립 전제 (지금은 1~3장만 채워도 동작).
3. **데이터 과수집.** 지금 안 써도 멀티뷰·3D가 나중에 먹는 재료를 미리 모음.
   - 의류: 앞 + 뒤 (가능하면 옆)
   - 사용자: 원본 고해상 캡처 + 포즈/파싱 맵 + (도입 시) SMPL-X 피팅
4. **PyTorch / diffusers 표준화** — 새 논문 모델 드롭인 용이.
5. **모델 = 원격 워커** — 백엔드는 큐에 작업 투입, GPU 워커가 처리해 번들 반환.

## 9. 단계별 빌드 계획 (기간 없음, Phase 단위)

각 Phase는 "돌아가는 결과물" 하나로 끝남.

### Phase 0 — 토대 + 학습 루프 (맥)
- 앱 골격: 카탈로그/CMS, 키오스크 프론트(목록→선택→결과 뷰어).
- 백엔드에 `TryOnEngine` 인터페이스 + **더미 워커** + 작업 큐 플러밍(모델 전에 먼저).
- 결과 뷰어를 미디어 번들 + N앵글 스와이프 전제로 구현(1장만 와도 동작).
- 전처리 모듈 인터페이스 확정 (전처리 = 마스크 생성. 무거운 구현은 Phase 1 클라우드 GPU).
- 학습: 맥에서 diffusers 기본 SD 1회 실행 (`experiments/sd_inpaint_smoke.py`).
  IDM-VTON·CatVTON repo/논문(arXiv 2407.15886) 정독.
- **완료 기준:** 상품 선택 → (더미) 결과가 뷰어에 뜨고 좌우로 넘어간다.
  \+ TryOnEngine/번들 스키마와 전처리 모듈 인터페이스가 명확히 정의돼 있다.

### Phase 1 — 이미지 VTON 실작동 (클라우드 GPU)
- GPU 임대. **CatVTON**부터 세움, 이후 IDM-VTON 비교.
- 전처리 파이프라인(휴먼 파싱+포즈+마스크) 구축·컨테이너화 — 진짜 일감.
- 큐 워커에 연결, 더미 → 실제 모델 교체.
- 마네킹 모드(사전 캐싱) + 사용자 정면 모드 둘 다 실제 출력.
- 미래 훅: 전처리 산출물 전부 저장.
- **완료 기준:** 옷 사진 + 정면 사진 → 정면 착용 이미지 자동 생성.

### Phase 2 — 온보딩 + 캐싱 + 제품화 (맥/백엔드)
- 점주 온보딩: 의류 업로드 → 자동 배경제거/정규화 → 스톡 모델 다앵글 사전 합성 enqueue.
- 멀티테넌시 + 기본 결제.
- 키오스크 뷰어: 캐싱된 N앵글 화살표 전환(= 이산 회전 UI 골격).
- 단계적 과금 설계.
- 실매장 1~2곳 파일럿.
- **완료 기준:** 점주 셀프 등록 → 손님이 마네킹/본인 착용을 본다.

### Phase 3 — 파인튜닝 / 모델 소유 (클라우드 GPU) — 해자 시작
- 데이터 수집(파일럿 + 공개셋 VITON-HD, DressCode).
- CatVTON/IDM-VTON LoRA/파인튜닝 — 평면 앞·뒤 입력에 특화.
- 평가 하니스: 의류 충실도(로고/프린트 드리프트) 회귀 테스트셋.
- **완료 기준:** 자체 튜닝 모델이 베이스 대비 충실도·일관성 우위(측정 가능).

### Phase 4 — 멀티뷰 / 이산 회전 (클라우드 GPU) — 연구 인접
- VTON360 류: SMPL-X 노멀맵 → 다중 뷰 일관 VTON.
- 앞·뒤 의류 사진으로 정면/후면 뷰 확보.
- 이산 앵글 세트(0°/±45°/±90°/180°) 생성 → 뷰어 투입.
- 미래 훅: 멀티뷰 출력 + SMPL-X가 3D 단계의 조건/학습 신호.
- **완료 기준:** 한 의류를 여러 각도에서 일관 착용, 뷰어에서 돌려봄.

### Phase 5 — 영상 / 자유 회전 / 나풀거림 (클라우드 GPU) — 프론티어 / 미래 옵션
- **(a) 영상 VTON**: ViViD/SwiftTry/CatV2TON으로 도는 클립 + 나풀거림 오프라인 렌더. 비교적 달성 가능.
- **(b) 3D 경로**: HumanOrbit → 메시, 또는 HumanLift식 3D-GS로 진짜 자유 회전.
  뒷모습은 상상 영역 — 캡처한 뒷면 사진으로 제약 주거나 한계 수용.
- **왜 재작성이 아닌가:** Phase 1~4에서 미디어 번들 + N앵글 뷰어 + 멀티뷰·SMPL-X·뒷면 사진을
  쌓아뒀으므로, 클립/3D 에셋을 기존 파이프라인에 *끼워넣는* 작업이 됨. (설계 원칙 전체의 목적.)
- **완료 기준(장기):** 회전 클립 재생 또는 슬라이더 자유 회전 프로토타입이 뷰어에 붙음.
